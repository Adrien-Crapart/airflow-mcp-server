An MCP (Model Context Protocol) server exposing tools to manage an Apache Airflow
instance via an HTTP API (FastAPI). This repository includes handlers, the
Airflow client, and both unit and integration tests.

## Quickstart (Windows PowerShell)

```powershell
# Install uv (if needed)
powershell -ExecutionPolicy ByPass -Command "irm https://astral.sh/uv/install.ps1 | iex"

# Sync dependencies and create the virtual environment
uv sync

# Activate the environment (Windows PowerShell)
.venv\Scripts\Activate.ps1

# Run the server in development mode
uv run uvicorn airflow_mcp_server.server:create_app --factory --reload --host 127.0.0.1 --port 8000
```

## Exposed capabilities

The server exposes the following MCP tools:

- DAGs
	- `airflow_dag_list` — list DAGs
	- `airflow_dag_trigger` — trigger a DAG
	- `airflow_dag_pause` / `airflow_dag_unpause` — pause / unpause a DAG
- Tasks
	- `airflow_task_list_instances` — list task instances for a `dag_id`/`run_id`
	- `airflow_task_retry` — request a retry for a task
- Logs
	- `airflow_task_logs` — fetch logs for a task
- Connections
	- `airflow_connection_create` — create / update a connection
- Health
	- `airflow_health_check` — MCP server health
- Discovery
	- `airflow_tools_list` — list available tools (module, category, read_only, schema, examples)

Detailed capability documentation is available at `docs/mcp_capabilities.md`.

## Endpoints and discovery

- `POST /tool/{tool_name}` — invokes an MCP handler. Expected payload: `{ "params": { ... } }`.
- `POST /tool` — fallback endpoint accepting `{ "tool_name": "...", "params": { ... } }`.
- `GET /health` — liveness probe for the MCP API process.
- `GET /ready` — readiness probe that validates live connectivity to Airflow.
- Interactive OpenAPI UI: `GET /docs` (auto-generated by FastAPI).

To discover available tools dynamically, call the discovery tool:

```bash
curl -s -X POST http://localhost:8000/tool/airflow_tools_list \
	-H 'Content-Type: application/json' -d '{"params": {}}' | jq .
```

Or via the fallback endpoint:

```bash
curl -s -X POST http://localhost:8000/tool -H 'Content-Type: application/json' \
	-d '{"tool_name": "airflow_tools_list", "params": {}}' | jq .
```

## Agent and transport compatibility

The server supports multiple transport modes controlled by `MCP_TRANSPORT`:

- `http` — exposes `/tool*` and MCP Streamable HTTP on `/mcp`.
- `stdio` — process transport for local MCP clients (for example Claude Desktop).
- `both` — enables both modes (default).

Compatibility matrix:

| Agent type | Recommended transport | Notes |
| --- | --- | --- |
| Agents supporting MCP Streamable HTTP | `http` (`/mcp`) | Best option for remote production deployment |
| Agents calling custom HTTP actions | `http` (`/tool/{tool_name}`) | Legacy-compatible invocation model |
| Agents supporting MCP stdio only | `stdio` | Run process mode; not suitable behind a remote HTTP reverse proxy |

The container entrypoint now starts `python -m airflow_mcp_server.main`, so `MCP_TRANSPORT` is honored in Docker too.

## Examples (curl)

Call a tool (general structure):

```bash
curl -s -X POST http://localhost:8000/tool/{tool_name} \
	-H 'Content-Type: application/json' \
	-d '{"params": {...}}' | jq .
```

Concrete examples:

- List DAGs

```bash
curl -s -X POST http://localhost:8000/tool/airflow_dag_list \
	-H 'Content-Type: application/json' \
	-d '{"params": {"limit": 100, "offset": 0}}' | jq .
```

- Trigger a DAG

```bash
curl -s -X POST http://localhost:8000/tool/airflow_dag_trigger \
	-H 'Content-Type: application/json' \
	-d '{"params": {"dag_id": "example_bash_operator", "conf": {}}}' | jq .
```

- Fetch task logs

```bash
curl -s -X POST http://localhost:8000/tool/airflow_task_logs \
	-H 'Content-Type: application/json' \
	-d '{"params": {"dag_id": "my_dag", "run_id": "my_run", "task_id": "my_task", "try_number": 1}}' | jq .
```

- Create a connection

```bash
curl -s -X POST http://localhost:8000/tool/airflow_connection_create \
	-H 'Content-Type: application/json' \
	-d '{"params": {"conn_id": "my_conn", "type": "http", "host": "example.com", "login": "u", "password": "p", "port": 123}}' | jq .
```

## Environment variables

- `AIRFLOW_BASE_URL` (default `http://localhost:8080`)
- `AIRFLOW_USERNAME`, `AIRFLOW_PASSWORD` (BasicAuth credentials; empty by default)
- `AIRFLOW_API_TOKEN` (optional Bearer token for Airflow API)
- `MCP_SERVER_HOST`, `MCP_SERVER_PORT` (MCP server configuration)
- `MCP_REQUIRE_AUTH` (default `true`; protects `/tool*` and `/mcp`)
- `MCP_AUTH_TOKEN` (required for non-local/remote agents when auth is enabled)
- `MCP_ENABLE_ADMIN_ENDPOINTS` (default `false`; controls config/admin exposure)
- `MCP_READ_ONLY` (default `false`; hides mutating tools when enabled)
- `MCP_TRANSPORT` (`stdio`, `http`, or `both`; default `both`)
- `MCP_PORT_BIND` (default `127.0.0.1:8000`; host binding for container port 8000)
- `TRAEFIK_ENABLE` (default `false`; enable routing labels for Traefik)
- `MCP_PUBLIC_HOST`, `ACME_EMAIL`, `RATE_LIMIT_AVERAGE`, `RATE_LIMIT_BURST` (used with edge profile)

## Production deployment (Docker Compose)

One compose file is used for both local and production scenarios.

Local run:

```bash
docker compose up -d --build
```

Production (remote agents) with TLS/reverse proxy:

```bash
cp .env.production.example .env.production
# Edit required values: MCP_PUBLIC_HOST, ACME_EMAIL, AIRFLOW_BASE_URL, MCP_AUTH_TOKEN
docker compose --profile edge --env-file .env.production up -d --build
```

This single compose setup provides:

- Mandatory `MCP_AUTH_TOKEN`
- TLS termination (Traefik + Let's Encrypt)
- HTTP rate limiting middleware
- `/ready` healthcheck wired in container orchestration

Quick validation:

```bash
curl -s https://<MCP_PUBLIC_HOST>/ready | jq .
curl -s -X POST https://<MCP_PUBLIC_HOST>/tool/airflow_tools_list \
	-H "Authorization: Bearer <MCP_AUTH_TOKEN>" \
	-H "Content-Type: application/json" \
	-d '{"params":{}}' | jq .
```

## Tests

Activate the virtual environment and run the test suite:

```powershell
.venv\Scripts\Activate.ps1
.venv\Scripts\python.exe -m pytest -q
```

Run integration tests only (set `AIRFLOW_BASE_URL` if needed):

```powershell
#$env:AIRFLOW_BASE_URL = 'http://localhost:8080'; .venv\Scripts\python.exe -m pytest tests/integration -q
```

Integration tests include a fixture that automatically falls back to an HTTP mock
only when explicitly enabled. By default, integration tests require a reachable
real Airflow instance. Set `AIRFLOW_INTEGRATION_ALLOW_MOCK_FALLBACK=true` to
allow mock fallback for contract-style runs.
You can tune probe speed with `AIRFLOW_INTEGRATION_TIMEOUT_SECONDS` (default: `10`).

## CI

A GitHub Actions workflow is provided at `.github/workflows/ci.yml` to run
the unit test suite on Python 3.10 and 3.11.

CI now runs integration tests against a real ephemeral Airflow 3 service
started inside the workflow:

- Unit job runs only non-integration tests (`-k "not integration"`)
- Integration job starts `apache/airflow:3.0.2` in standalone mode
- The workflow reads the generated admin password from container logs, mints a Bearer token via `/auth/token`, and exports it as `AIRFLOW_API_TOKEN`
- Integration tests run with `AIRFLOW_INTEGRATION_ALLOW_MOCK_FALLBACK=false`

## Contributing / adding a tool

1. Create a new module in `airflow_mcp_server/handlers/` that exports a `TOOLS` dict mapping tool names → coroutine handlers.
2. Add a Pydantic model (if useful) in `airflow_mcp_server/schemas.py` and register it in `TOOL_INPUT_MODELS`.
3. Add unit tests in `tests/unit/` and optional integration tests in `tests/integration/`.
